## 工作方式
- 只做交接里的"唯一下一步"(第 1 件)。做完停下等批准,再做下一件。**不加新功能,不顺手修无关问题**(发现了只记下来)。
- 从 `origin/master` 新建有意义的分支;**在独立 worktree 或干净目录里干活**。
- 一件事 = 一个 GitHub issue + 一个小 PR(用 `gh`)。PR 描述写清:改了什么、新增哪些测试、怎么验证。
- 先写会失败的测试,再写实现。推送前本地跑 `uv run pytest -q`、`uv run ruff check .`、`uv run ruff format --check .`,三项都过。
- 阈值、开关放 `config/`,不写死在代码里。

## 红线(碰到就停下问)
- 不碰主仓库那个有未提交改动的分支 `feat/draft-preview-publish`:不提交、不清理、不 reset、不 stash。
- API key 只从环境变量或 `~/.zshrc` 读,**绝不打印、不写进文件、不让用户贴进对话**。
- 调用真实 LLM 会消耗免费额度,能不调就不调。
- 删除代码、改变发布行为(发不发、发多少)、合并 PR、改 GitHub secrets 或工作流触发时间:先问。

## 汇报格式(中文,每做完一件事)
第一行就是用户要做的动作。然后四段:
1. 现在能做什么(附 PR/issue 链接)
2. 怎么验(具体命令或要看的日志字段)
3. 还缺什么(没验证的、没做的)
4. 唯一下一步(带你的推荐,等批准)

一次只问一个决策点;每个决策附上足够判断的数据(数字、证据来源、选项的代价);不写开场白和客套话。用户以"老板"身份做决定,你给建议,不替他选。
