## 二、外部架构评审:总评 C-

每个步骤单独写得还行(打分/配额/渲染基本是纯函数,测试全绿)。问题在把步骤串起来的那一层:
**定稿重新采集一遍、状态放在不可靠的缓存里、失败不出声。** 四个月里大量时间花在排查
"跑成功了但结果不对",根源是这三条,不是能力问题。

### 最严重的问题(按代价排序)

| # | 问题 | 为什么重要 | 最小修法 | 工作量 |
|---|---|---|---|---|
| 1 | 定稿不读白天的卡片,整条链重跑一遍再按链接对决策 | 你保留的条目晚上若掉出前 60 或解读失败,会被悄悄丢;白天晚上各解读一遍,额度白烧 | 定稿直接读 `pending_reviews` + 决策表 | 2–3 天 |
| 2 | 状态库在 Actions 缓存里,无并发保护,后写覆盖先写 | 已发布记录、解读缓存、来源权重可能静默回滚 → 重复发布、权重重置 | 三个工作流加同一个 `concurrency` 组(一行);中期换存储 | 0.5 + 1 天 |
| 3 | 失败不出声 | 决策拉取失败当成零决策出空稿;`runs.status` 从不更新;`publish.yml` 用了不存在的参数并吞掉报错,**从未成功过** | 运行结束健康检查:成功率过低/拉取失败/0 条 → Telegram 告警 + 任务失败 | 1 天 |
| 4 | `cli.py` 里编排写了两份且不一致;`--tick` 无视 `--dry-run` | dry-run 量出的数字和生产不是一回事 | 合成一个 `build_pipeline(mode)` | 2 天 |
| 5 | CLAUDE.md 写的架构一半不存在 | agent 按假说明继续写代码 | 改文档说真话 | 0.5 天 |
| 6 | 最关键依赖是会限流的免费 LLM | 质量上限由额度决定 | 只解读最终会发的约 12 条(配合 #1 自然实现) | 随 #1 |

| 8 | 配置文件被当成变更日志 | 难读 | 历史挪进 git log / ADR | 0.5 天 |

### 可以删掉的(约 1,200–1,500 行)
selfcheck(生产从不调用)、storylink(从未合并过一次却每晚调 LLM)、审阅层的 edit 路径、
一批没人用的旧接口、7 个 `run_dry_*` 函数、重复的 `_filter_evidence`。

### 做得好、应保留的
纯函数的打分/配额/渲染 + golden 测试;LLM 适配器的报错分类;零产出告警、解读缓存、
无锚点不采用;source 注册表 + `sources.d`;人工确认门。

### 评审建议:如果只做三件事
1. 工作流加 `concurrency` 组 + 运行结束健康检查;修好或删掉 `publish.yml` 那一步。
2. 定稿改成读白天的卡片和决策,不再重新采集。
3. 编排合成一条可注入依赖的流水线,删掉 dry-run 副本和死代码,更新 CLAUDE.md。
