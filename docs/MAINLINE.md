## P0:finalize 跑一次要 40-60 分钟

2026-09-03/04 连续两晚,用户等到深夜,原话"这他妈卡在哪里了"、"每天都这样,那我还发不发了今天"。

根因两条叠加,**其中一条是我造成的**:

1. 我把 `card_pool_limit` 50→100 时**只算了 LLM 调用次数的成本,没算墙钟时间**。`interpret()` 是纯顺序 for 循环,一条一条等 LLM 返回,100 条就是 100 次串行往返。
2. 同期 ModelScope / agnes 本身不稳(400 / 500 / 超时),每条要重试更久。

**修法不是把发卡池缩回去**——那会把刚救回来的 X 覆盖率(2/50 → 20/50)搭进去。正确修法是让 interpret 并发跑:调用次数与成本完全不变,墙钟从「N × 单条延迟」降到「N/并发 × 单条延迟」。未做,未验证。

### X / 内容具体问题(2026-08-27 用户点名,三条) — 三条均已 SHIPPED(#119 / #117 / #105)

#### 1. 同一事件多源重复:原发布 + 第三方"已支持"公告应合并成一条

例:A 公司发布某模型,随后多个第三方平台各自发"我们已支持该模型"——现状是每条都当独立新闻打分发布,读者看到的是同一件事被拆成好几条卡片。这跟 KANBAN #73(故事线合并)是同一类问题的具体案例,#73 原描述偏"多家媒体报道同一事件不同措辞",这次用户点出的是**原发布方 vs 下游第三方跟进支持公告**这种更具体的模式,需要在故事线合并设计时把这个模式也覆盖到,不是简单查标题相似度。

#### 2. 低置信度的公司名/模型名需要 fact-check,不能直接采信

跟本次已经查实的 `x-ai-company`→"xAI" 编造是同一类风险的更一般化表述:不只是 source slug 泄漏这一种触发方式,任何模型/公司名判断不确定的场合都需要一道"低置信度就别写死"的机制,而不是等撞名了才发现。这跟 KANBAN #69(内容确定性/信息密度打分维度)是同一根因但目标更明确——#69 原描述偏"给空洞内容降分",用户这次要的是**主动 double-check/fact-check 机制**,让 LLM 对自己不确定的实体名要么不写死、要么有二次校验,而不只是打分降权。两条建议合并到同一次 `/brainstorm` 一起设计。

#### 3. GitHub Releases 时效性:几天前的 release 当"今天"发(已 SHIPPED)

**已用代码验证根因**(不是猜测):`CollectionConfig.window_hours` 默认全局 72 小时,是为了不漏抓 paper/tool/blog 这类慢更新源才拉宽的,连带放行了 2-3 天前的 github_releases。**2026-08-27 SHIPPED(#105)**:新增 `window_hours_by_adapter`(默认 `{"github_releases": 48}`),按 adapter 查表取更紧的窗口,其余 adapter(paper/blog 等)不受影响。真实 collect 数据验证:比旧配置少收 11 条 48-72h 前的旧 release,37 条 ≤48h 的条目原样保留。
