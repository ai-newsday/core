# Manager 汇报

Boss 要的不是过程叙事, 是**能决策的信息**。这个 skill 规定收尾长什么样。

## 一、事实标记(最重要的一条)

每条有后果的陈述必须能被归到三类之一。写的时候不必加标签, 但**心里要能归类**;
归不了类的话, 说明你在把猜测当结论说。

| 类别 | 判据 |
|---|---|
| **[已验证事实]** | 有当前仓库、跑过的命令、真实运行日志或实测数据支撑 |
| **[提案]** | 你的设计/取舍/建议, Boss 尚未表态 |
| **[已决定]** | Boss 明确接受过的约束或选择 |

两条硬规矩:

- **不得把提案写成既定事实。**
- **不得从沉默推断批准。** 没回答 ≠ 同意。

### 这条规矩挡的是什么(真实案例)

- `#134`: issue 里把 `ltx_role_affiliation` 写成 "direct, structured"、"unambiguous"。
  实测那个字段装的是标签词加一个残留的 `[`, **10 篇论文提取到机构名的 0 篇**。
  那句话是提案写成了事实, 而且是我自己写的 issue, 差点按它去实现。
- `#175`: 原方案是"按账号做同源惩罚"。量完发现被投诉的三条是 77/70/69 分, 而发卡池
  第 12 名是 90 分 —— **它们能进成品是因为用户按了 keep, 跟分数无关**, 惩罚这个杠杆
  根本够不着。方案在写进 issue 时就该标成提案。

## 二、一次只问一个问题

发现需要 Boss 拍板的取舍时, **一次只提一个, 然后停下等**。

一口气抛三个选择题, 实际结果是 Boss 只回答其中一个, 另外两个悬着, 而你会倾向于
把没回答的那两个当成"默认同意"继续做 —— 那就是从沉默推断批准。

如果同时冒出多个决策点: 挑**阻塞下一步的那个**问, 其余写进 KANBAN 的待决策区。

## 三、收尾五段

每个工作单元结束(不只是会话结束)按这个结构:

```
1. 做了什么     —— 一句话一件事, 不写过程叙事
2. 状态         —— 完成 / 部分完成 / 受阻(受阻要写卡在哪)
3. 产物         —— 可点击: PR、issue、文件路径、线上链接
4. 证据强度     —— 通过 / 需修改 / 证据不足(自评, 见下)
5. 下一个决策点 —— 唯一一个, 然后停
```

### 第 4 段"证据强度"怎么自评

这一段是给自己的照妖镜, 别跳过:

- **通过** —— 有实测数据支撑, 而且数据是**改动之后**跑出来的
- **需修改** —— 能跑但有已知缺口, 写清楚缺口
- **证据不足** —— 测试全绿但没验证过真实效果。**这不是失败, 是必须说出口的状态**

"测试全绿"永远不等于"通过"。`#146` 的标题选题规则测试全绿, 但当晚 provider 故障,
模型到底认不认那套规则**至今没验证过**; 汇报时说成"生效了"就是把证据不足报成通过。

## 四、先量再改

在提出方案前, 先确认方案依赖的信号真的存在、真的够用。这条在本仓库反复兑现:

- 配图按体积过滤 —— 实测图标 101KB **比真插图 38KB 还大**, 方案作废
- 抓 README 补机构 —— 三个真实页面里一个只有 shields.io 徽章, **会把徽章当配图**, 作废
- 故事线合并 —— 实体正则拿 10 个真实模型名测**只匹配 2 个**, 该特征基本空转

四次里三次推翻了动手前的方案。**先量的成本远低于白干的成本。**

## 五、看板与代码同批

工作单元完成时, KANBAN / MAINLINE 的更新**跟代码走同一个 PR**。

拖到"之后再补"的结果是漂移几周; 本仓库已经因此补过两次大的追平。

## 反面清单

出现这些念头就停:

| 念头 | 实际含义 |
|---|---|
| "顺手把这个也改了" | 静默扩大范围, 先问 |
| "他应该会同意" | 从沉默推断批准 |
| "测试绿了就是好了" | 证据不足报成了通过 |
| "先做完再一起汇报" | Boss 失去中途纠偏的机会 |
| "这几个问题一起问了省事" | 会有问题悬空, 然后被当成默认同意 |
